# 本地回复延迟诊断 · 2026-10-19

后续优化已实现，最新结果见 [回复加速验收](ACCEPTANCE-REPLY-SPEED.md)。下文保留优化前的诊断数据。

本次只增加阶段计时并测量瓶颈，尚未更换音色、生成模型或启用流式播放。服务通过 `/api/health`，现有面部融合保留。

## 测量方法

通过真实 WebSocket `user.text` → 本地 Dolphin → 现有 CosyVoice2 克隆语音 → PCM 接收测试，排除硬件麦克风和额外人物会话。每次等待上句结束，测短句、长句；再单独测合成期间发送新文字打断旧回复。测试使用 browser 音频路由，不会把测试语音发送到用户的数字人会话。收到 PCM 不等于测量到了扬声器首声，实际端到端还包括播放缓冲。

```bash
.venv/bin/python scripts/diagnose-reply-latency.py
.venv/bin/python scripts/diagnose-reply-latency.py --interrupt-only
```

## 实测

| 受控回复 | 收到第一段音频 | 音频长度 | 文字生成 | 合成锁等待 | 语音合成 |
|---|---:|---:|---:|---:|---:|
| 12 字短句 | 6.60s | 2.48s | 0.956s | 0s | 5.642s |
| 45 字长句 | 19.00s | 8.96s | 2.361s | 0s | 16.633s |
| 打断长句后回复“好的。” | 20.04s | 1.20s | 0.561s | 13.022s | 4.431s |

45 字长句合成细分：语音 token 生成 11.862s（224 tokens，MPS），声学 Flow 阶段 3.496s（包括 Core ML 和数据传输），HiFT 声码器阶段 1.253s（CPU）。Flow 计时到 mel 传回 CPU 为止，覆盖异步 GPU 计算；HiFT 计时含缓存处理。语音 token 生成约 18.9 tokens/s，而该段音频为 25 tokens/音频秒；单是 token 生成就慢于实时。完整语音合成 RTF 约 1.86。

用户实际日志中，普通语音识别 0.467–0.630s，曾有一次 3.003s；端点检测配置还需约 600ms 静音确认。识别后到语音就绪曾等待约 17–30s。人物日志稳定约 25fps，不是这段等待的主要来源。

## 根因

1. `chunk_ms: 0`：等待整段文字，再合成整段语音，全部完成后才发第一段音频。字幕同样等音频就绪才释放，界面会长时间像是没有回复。该模式保住了当前连续播放效果，但增加首声等待。
2. CosyVoice 自回归语音 token 解码是最大计算开销。它已在 MPS 上执行；Flow 已有 Core ML 路径，不能将问题归因为完全未使用 Mac GPU。
3. `abort` 只让旧回复的输出被丢弃，没有中止底层 `tts.synthesize()`。旧合成继续持有 `_synthesis_lock`，新回复排队。打断后先等待旧回合收尾的约 2s，再叠加锁等待和新合成，实测约 20s。
4. 另有会话隔离隐患：服务全局只有一个编排实例，`run_ws()` 每次连接都重置同一份状态。双标签页或切换模式的新旧连接可互相影响。无并发的受控测试也能复现延迟，所以这不是主要计算瓶颈。

## 下一步顺序

先让取消贯穿语音 token 生成、Flow 与队列，尽快释放旧合成资源；同时隔离不同连接的会话状态。随后对语音 token 解码单独加速、测相同音色和长度。最后改成有预缓冲的渐进播放，明确区分生成中和播放中，并测首声与连续性。

不能只切 `chunk_ms > 0` 就认为问题解决：现在生产速度低于实时，直接播放可能重新引入句中卡顿；现有 Core ML Flow 包装器在 `streaming=True` 时还会回退原始实现。必须同时验证生成吞吐与音频连续性。

原始证据：`logs/reply-latency-results.json`、`logs/reply-latency-interrupt-results.json`、`logs/mac-latency-20261019.log`。这些数值是本机实测样本，长短句和随机采样会影响结果，不代表固定延迟保证。
