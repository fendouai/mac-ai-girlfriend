# 环境声、断句和回复等待 · 2026-10-19

## 结论

可以优化，但“麦克风电平一直在动”不能单独证明噪声正在拖慢回复。网页的电平条来自 `mic-capture.js` 的门前 RMS，噪声门关闭后仍会显示收到的原始音量。实际送到后端的 PCM 则经过门控；浏览器还请求了回声消除、降噪和自动增益。

当前默认噪声门为 `-50 dBFS`，保存在浏览器的设置可以覆盖默认值。本次无法读取当前浏览器的实际门限，也没有录制或读取用户现场麦克风音频，因此不把模拟测试当作现场噪声鉴定。

后台当前 VAD 概率门限 0.5，持续人声确认约 350ms，连续非人声约 600ms 才结束一句话。背景人声和扬声器回声容易通过“是否有人声”的判断；如果被当作用户继续讲话，就延后断句；如果发生在回复生成或播放中，就可能取消回复。

## 离线样本测试

使用当前 Silero VAD 和相同端点参数；输入为现有合成语音、模拟底噪和敲击，不启用硬件麦克风、不建立新对话，也不重启运行服务。

测试直接向后端检测器送音频，没有经过真实浏览器的 AEC / 降噪。背景人声来自已有生成音频，电平约 -38 dBFS；测试描述的是检测器可能出现的行为。

| 样本 | VAD 结果 |
|---|---|
| 静音 | 无开口事件 |
| 模拟风扇底噪，约 -35 dBFS | 无开口事件；最高人声概率约 0.062 |
| 短促敲击 | 无开口事件；最高人声概率约 0.079 |
| 轻背景人声 | 触发完整发言事件，最高人声概率接近 1 |
| 正常语音 | 在测试音频时间 3.968s 判断结束 |
| 正常语音 + 风扇底噪 | 同样在 3.968s 判断结束 |
| 正常语音 + 敲击 | 同样在 3.968s 判断结束 |
| 正常语音后有背景人声 | 在 8.576s 才判断结束，较干净样本延后 4.608s |

这组样本说明背景人声确实能延后回复入口；不能推广为任何风扇或键盘声音都不会误触发。

## 实际日志还能说明什么

本次重启后的几句短对话，识别耗时大致 0.27–0.54s，语音合成约 2.8–3.8s。也出现了识别为“本地的光。”的输入与多次取消；日志没有保存原始录音、逐帧 VAD 概率或 RMS，无法据此认定哪一次是本人说话、背景声还是回声。

另一个已确认的慢点是长回复：讲笑话请求产生约 161 字回复，LLM 约 18.68s，TTS 任务运行约 38.98s 后被取消；另一条约 166 字回复，LLM 约 18.38s，TTS 约 35.57s 后取消。由于当前整段合成后才播放，长回复会造成明显首声等待。这与环境杂音是两条不同的延迟路径，不能只用提高门限解决。

## 优化顺序

1. **先补充判定证据**：记录发言开始/结束、门后 RMS、VAD 置信度、取消原因和各阶段时间，按连接关联；不需要默认保存原始录音。这样才能区分“还没断句”“噪声取消了回复”和“长回复仍在生成”。
2. **自适应噪声门**：仅在高置信非人声时估计底噪，使用动态余量和限幅，保留轻声、字首与字尾；不能把真正的轻声逐步学成噪声。
3. **起止阈值与插话确认分开**：结束判定采用迟滞；回复期间对疑似插话增加置信度/持续性校验，并结合已播放音频判断回声，保留用户主动打断。
4. **控制超长发言和回复**：给无限延长的输入段加入保护；将长篇答复按自然边界生成和预缓冲播放。分段需同时测连续性与口型，不仅测首包时间。

不宜直接把门限提高很多，或只把静音判定由 600ms 改得很短：前者会吞轻声，后者会把正常停顿拆成多句。前端门控还有 250ms hold 和约 80ms release，它们与 VAD 的延迟并非机械相加，取决于实际声音何时不再被判为人声。

该诊断阶段没有修改拾音门限或 VAD 参数。随后按用户要求加入短回复策略：通常 10～24 字，最多两句、40 字；需要更多内容时说“继续”。背景声门控与插话二次确认仍是待实现的优化方向，不能把短回复策略当作已完成降噪。
